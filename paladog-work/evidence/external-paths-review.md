# External path audit of the supplied Paladog APK

Scope: static review of `jadx/sources` plus caller checks in `decoded/smali`; no APK execution. This records the original supplied bytecode, not a developer-source reconstruction. Decompiled source line references below are relative to `jadx/sources`.

## Reachable startup and foreground paths

1. `com/Paladog/KorGG/Paladog.java:99` (`onCreate`) initializes the game. Lines 123–145 read `getDeviceId()` and `getLine1Number()`, then assign `Build.MODEL` and a fallback telephone number. Replace this whole identity-assignment block with a stable local identifier and empty telephone string; leave game screen/save initialization after it intact. Do not just remove the phone permission: these calls can throw before the game starts.
2. `Paladog.java:167–169` unconditionally binds the Play billing service through `com.android.vending.billing.InAppBillingService.BIND`, explicitly packaged to `com.android.vending`. `onDestroy` unbinds at 245–246. Remove the bind and corresponding unbind together. This is Binder delegation; removing INTERNET does not prevent it. `BuyItemActivity` / `BuyCashItem` must terminate in the existing non-success purchase state, never award currency or report a successful purchase.
3. `Paladog.onResume` calls `checkCheat` at 229. `checkCheat -> checkCheatApp` (665) first calls `DownloadCheatFile` (730), which fetches `SP.SERVER_ADRESS_CHEAT_INFO` (`http://kakao.palamini-game.com/paladog/paladog_cheat.txt`). It then executes `ps` and enumerates `ActivityManager.getRunningAppProcesses`. No-op `checkCheat` and/or make `checkCheatApp` return false to eliminate the remote list and app/process inventory; also stub its downloader as defense in depth. This is independent of marketing consent.
4. `com/my/Layer/MainMenuLayer.java:184` constructor unconditionally calls `Paladog.registerGcm()`. Confirmed in Smali at `MainMenuLayer.smali:465`. `registerGcm` checks the manifest and registers via Google service APIs. Therefore it must be stubbed before deleting GCM manifest entries; otherwise `GCMRegistrar.checkManifest` can fail on the stripped configuration.
5. `GCMIntentService.onRegistered/onUnregistered -> sendServerRegID` (`com/Paladog/KorGG/GCMIntentService.java:27,32,65`) submits the registration token and operation flag to `http://kakao.palamini-game.com/push/set_push.php`. The manifest independently exposes `GCMBroadcastReceiver` and `GCMIntentService`. Remove their declarations and C2DM permission declarations; stub `registerGcm` and `sendServerRegID` as well.
6. `MainMenuLayer` update calls `BannerModeProc` at 1263. The initialized `iBannerMode=0` advances to 3, fetching `SP.SERVER_ADRESS_BANNER_INFO` at 5375 (`http://kakao.palamini-game.com/paladog/paladogbanner_google1.txt`). Parsed response fields control banner image selection and `szBannerLink`; this is a real reachable promotion path, not merely an unused URL constant. Stub `BannerModeProc`, setting the banner mode disabled and URLs empty if desired.
7. Loading marketing/certification uses `Library.DownloadHtml`: `LoadingLayer.java:314–316` builds a request containing telephone, model, app version and carrier; lines 319–350 show the SMS consent UI and the explicit `zamburgers.com` opt-in request. The UI is a separate change from blocking transport. The loader must follow its normal local-game state after suppressing the prompt; do not leave its wait state active.

## External browser and login paths

- `MainMenuLayer.ccTouchesEnded` at 2175–2181 launches ACTION_VIEW for the downloaded banner URL. Suppress the invocation even if the banner state is disabled, so stale state cannot open a browser.
- `MainMenuLayer.TouchEndUIProc`: ID 50 calls `AppDelegate.GotoPaladogTrailer()` (YouTube ACTION_VIEW at `AppDelegate.java:11554`). IDs 94, 95, 96 launch the QQ microblog, game site and forum through ACTION_VIEW (2430–2444). Disable these handlers and hide the corresponding buttons where practical. INTERNET removal does not stop the browser application from communicating.
- IDs 91/92 invoke Facebook login/logout. `AppDelegate.FacebookTryLogin0/1 -> ViewController.FacebookLogin0/1 -> Paladog.OpenFacebookActivity(19/20) -> FaceBookActivity` is a reachable path. The login button invokes `Facebook.authorize` with activity code -1 (forced WebView dialog), requests `publish_stream,user_photos,email`, then fetches `/me`. Facebook SDK also contains external-app SSO, but the reviewed game call uses the dialog variant. Stub the game entry point and remove the Facebook activity declaration after disconnecting callers. `OpenFacebookActivity` also has async HTTP operations for logout/profile/friend list.
- `ViewController` construction in `AppDelegate.Initialize` creates Facebook objects, but the reviewed Facebook constructor only saves an app ID and does not itself start a network operation. Removing the entire ViewController would break game references; keep it with external methods disabled.
- Hangame notice URLs at `MainMenuLayer.java:4340–4342` lead through `AppDelegate.NHNLineLaunchWithUri -> ViewController.onLaunchWithUri`, whose body is already empty. These strings do not establish a reachable network launch in this variant.

## Preserve existing offline survival

`MainMenuLayer.TouchEndUIProc` ID 130 opens campaign save slots. ID 131 applies existing Paladog/Darkdog survival unlock guards, then opens the chooser (UI 158–162). IDs 160 and 161 both set `m_iNeedMove=8` and enter the online login scene; 160 additionally selects Facebook. ID 162 is the existing offline option and calls `MsgBox(2,true)`, whose confirmation uses `StartSurvivalOffline()`. That method resets online score/account state, sets `m_iNeedMove=4`, and clears `bSurvivalWithFacebook` (`MainMenuLayer.java:4237–4255`). Preserve these unlock/progression guards and this local path. A game-only UI can route the guarded ID 131 flow to the same existing offline action, or suppress 160/161 while retaining 162. Do not stub the entire survival subsystem or mistake campaign ID 130 for survival.

## Central HTTP boundaries and save-file concern

- `com/common/Library`: `DownloadHtml(String)` and `DownloadHtml_Apache(String)` can return the established failure value (`null`) immediately; callers generally check null/empty. `HttpFileUpload`, `HttpFileDownload` and `GetServerXML` should be no-ops. Keep normal local serialization and SharedPreferences methods intact.
- Important: original `HttpFileDownload` opens a `FileOutputStream` to the target local `shared_prefs/*.xml` before trying the URL. Relying only on INTERNET denial could truncate a save if this routine were entered. An explicit no-op is safer. There is no direct caller of `GetServerXML` outside its own class in the examined Smali, so this is a defensive hardening of a dormant restore path, not evidence that current startup triggers it.
- `Library.networkCheck` calls `ConnectivityManager.getNetworkInfo(...).isConnected()` without robust permission/null handling. Return false when removing ACCESS_NETWORK_STATE. No direct app caller was found, but the boundary is safe to disable.
- `com/my/DB/Downloader.download` is another URL helper; return null immediately to prevent attempts through that helper.
- `AppDelegate.SurvivalLogTry` (7614) constructs a request with telephone, model, email, game kind, wave and kills. `buyItemTry` reports item purchases; `ClientLogSend` uploads a chosen SharedPreferences XML through `HttpFileUpload`. Transport stubs block these, but no-op the dedicated reporting methods if complete noncollection is desired.
- `ViewController.setURLImage` and `setLineURLImage` directly open profile-picture URLs outside `Library`. Return false without touching image files. Block account entry points rather than leaving a login spinner waiting forever.

## Bundled SDKs, native code and dynamic loading

- `Paladog.AppleJuiceActivity`, `AJViewProc` and `AJHonorProc` are already empty. `TencentProcLayer` calls the empty AppleJuiceActivity. `TestAJService.OpenLogin` calls `AJAuthService.LaunchAuthView`, but searches of original Smali found no caller of `TestAJService` outside that class itself. Therefore this report does not label the entire SDK as startup-reachable. Stubbing `TestAJService.OpenLogin` is a small defensive boundary change; wholesale SDK deletion is unnecessary for the minimum patch.
- No Google AdMob-style call was found in the game entry classes. The concrete reachable advertising/promotion behavior identified here is the game's own banner metadata/UI, distinct from a claim that every bundled SDK is malicious.
- Native load sites found in the decompiled APK are `com/appleJuice/AppleJuice.java` (`AppleJuice`), `com/kakao/api/util/SimpleEncryption.java` (`simpleencryption`), and `com/tenpay/android/des3/DES3.java` (`des3jni`). APK contains ARM 32-bit copies: `armeabi/libAppleJuice.so`, `armeabi/libsimpleencryption.so`, `armeabi/libdes3jni.so`, and `armeabi-v7a/libsimpleencryption.so`.
- No native call/load instruction was found in the reviewed core Paladog/common/my/SPC/org game packages. Apparent Kakao imports in game source are JADX's naming of inlined numeric constants; they do not demonstrate SDK initialization.
- Searches found no DexClassLoader, PathClassLoader, loadDex, or downloaded-code execution in this APK's Java/Smali view. Generic `Class.forName` in Base64 object decoding and support-library fragment class loading are not by themselves remote-code loading. This is a static finding, not a proof of absence of all dynamic/native behavior.

## Defense layers and limits

For the minimum offline build, retain only required local permissions (VIBRATE if vibration is kept), strip INTERNET, READ_PHONE_STATE, ACCESS_NETWORK_STATE, GET_ACCOUNTS, BILLING/CHECK_LICENSE and C2DM requirements, and disable external-facing components after their callers have been handled. WAKE_LOCK is only required for the removed GCM path in the manifest; the game uses window keep-screen-on flags. Local SharedPreferences saves do not require WRITE_EXTERNAL_STORAGE. Separately inspect screenshot functionality before deciding whether to preserve external storage support; it is not required by the save routines reviewed here.

Direct HTTP stubs + disabled Binder/browser/login entry points + manifest network/identity permission removal provide stronger coverage than URL removal alone. A successful build and static checks cannot establish that campaign, Darkdog, survival and save/reload all work; execution in a compatible isolated Android runtime remains required. The presence of dormant ARM libraries alone also does not prove the core Java game needs them, but an ABI/compatibility claim needs a separate tested build and runtime validation.
